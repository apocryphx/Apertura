# Session 2026-10-13 — M6 machine bring-up, GPU Neural Accelerators (NAX) A/B

Trigger: new machine on an **Apple M6** (12-core GPU, Metal 4, `applegpu_g18g`, 24 GB, macOS
27.0.1, Xcode 27.0). Question: do the M5/M6 GPU Neural Accelerators help Apertura? Answer: yes —
prefill 2-3× on every small model, decode unchanged, fidelity unchanged. Only small models fit
(E2B, E4B, 12B).

## Done
- Provisioned the machine from scratch (nothing was on it): `brew install cmake hf`; Xcode's
  **Metal Toolchain** component was missing (`xcodebuild -downloadComponent MetalToolchain`) —
  without it MLX's CMake prints a warning and builds **without NAX** (and no metallib at all);
  `sh Tools/bootstrap.sh` to init the ObjCTokenizer submodule; `sh Tools/build_mlx.sh` at the
  existing pin `d9add9d11` (v0.32.2-61), which already contains the NAX kernels (qmm, GEMM
  fused/gather/splitk/segmented, fp-quantized, steel attention). No pin bump needed.
- NAX gate in MLX: compile-time (Metal ≥ 4.0, SDK ≥ 26.2, deployment target ≥ 26.2 — the target
  defaults to the host OS, 27.0.1 here) + runtime `is_nax_available()` (GPU gen ≥ 17, ≥ 18 for
  'p' parts). The M6 passes both.
- A/B harness: second MLX build in `../mlx/build-nonax` with `-DCMAKE_CXX_FLAGS=-DMLX_METAL_NO_NAX`
  (same pin, same target — only the runtime gate off); AperturaResearch built twice via
  `MLX_BUILD=` override. Release CLI builds need `ARCHS=arm64 ONLY_ACTIVE_ARCH=YES` (universal
  link fails on x86_64 against the arm64-only libmlx.a).
- Bundles: `apocryphx/gemma-4-{E2B,E4B}-it-q4-apml` and `…-12b-it-qat-q4-apml` into
  `~/Documents/GitHub.nosync/Resources/Models/Apertura/`; E2B QAT source
  (`google/gemma-4-E2B-it-qat-q4_0-unquantized`, 9.5 GB) into
  `~/.cache/huggingface/sources/`. Downloaded with curl per file (size-checked against the HF
  tree API) because `hf` hung — see Network below.
- **Prefill** (`--bench-eager`, one arm per process, cold-gated die ≤ 52 °C via `Tools/hidtemp`,
  NAX vs no-NAX interleaved, tok/s; E2B sweep = median of 3, the others mean of 2):

  | Model | 256 | 512 | 1024 | 2048 | 4096 | 8192 |
  |---|---:|---:|---:|---:|---:|---:|
  | E2B | 1585 / 845 | 2184 / 937 | 2450 / 956 | 2477 / 943 | 2415 / 890 | 2112 / 800 |
  | E4B | | 1103 / 481 | | 1440 / 489 | | 1328 / 447 |
  | 12B | | 431 / 186 | | 591 / 186 | | 576 / 180 |

  → 1.9× at 256, 2.3× at 512, 2.6-3.2× from 1K up. Decode identical (qmv path, bandwidth-bound):
  E2B 68-78, E4B 36-41, 12B 15-18 tok/s. First NAX prefill in a fresh process pays a one-time
  kernel JIT (E2B @256: 415 tok/s / 0.62 s, discarded) — the app should warm up at load.
- **Fidelity**: E2B `--vs-bf16` NAX 115/116 + 255/256 (1653-tok War and Peace prompt), no-NAX
  116/116 + 253/256 (reproduces the archived 116/116). New PyTorch fixture
  `fixtures_e2b_qat` (E2B QAT checkpoint, MPS bf16, "The quick brown fox" — greedy is the
  self-repeating artefact) → CONFORMANCE PASS 14/14, argmax + greedy, unfused and fused, on
  both builds. Caveat: a 4-token prompt likely doesn't reach the NAX matmul paths; the
  long-prompt vs-bf16 is the one that exercises them.
- Kernel probe (scratchpad `probe.cpp`, linked against each libmlx, vs fp32 CPU reference):
  qmm x[2048,2560]·W[10240,2560] q4 g32 — identical error both builds (rel-L2 4.70e-3), 7.6 vs
  24.0 ms (14.1 vs 4.5 TFLOP/s, 3.2×). Causal SDPA [1,8,2048,256], 1 kv head — NAX rel-L2
  1.63e-3 (= the bf16 rounding floor of the reference itself), classic 3.61e-3.
- Greedy chat outputs of the two builds fork at bf16 near-ties (~100 tok into decode on a short
  prompt, ~60 on the 1.6K prompt), both continuations coherent — the token-match numbers in the
  README are kernel-path dependent at the near-tie level.
- PyTorch env: `~/.venvs/apertura-torch` (uv, Python 3.13 — Homebrew's 3.15 has no torch
  wheels): torch 2.14.1 (MPS), transformers 5.19.0, safetensors, accelerate, py-spy.
- README: new "GPU Neural Accelerators (M5 / M6)" section (table, decode/fidelity notes, the
  Metal Toolchain build trap); Requirements mention the toolchain; Build notes the arm64 flag.

## Network (machine-local, not a code issue)
- Every network-touching `hf` call hung (download, `auth login`, even with `--token`). Root
  cause: the Linksys router (`d8:ec:5e:82:76:46`, also the IPv4 gateway) advertised an AT&T
  IPv6 prefix (`…:22f::/64`) it didn't route; Python's HTTP stack waits on the AAAA address
  forever (socket in SYN_SENT), while curl/browsers fall back to IPv4 (Happy Eyeballs). Not the
  dual Ethernet + Wi-Fi setup — v6 failed on each interface alone. Kolja put the Linksys into
  IPv6 bridge mode; v6 now comes from the AT&T gateway (`3c:71:4b:09:7f:71`, `…:220::/64`) and
  works on both interfaces; plain `hf` works. `~/.local/bin/hf4` (IPv4-forced wrapper) remains
  as a fallback. HF login done by Kolja.
