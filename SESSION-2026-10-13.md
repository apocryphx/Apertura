# Session 2026-10-13 — M6 machine bring-up, GPU Neural Accelerators (NAX) A/B

Trigger: new machine on an **Apple M6** (12-core GPU, Metal 4, `applegpu_g18g`, 24 GB, macOS
27.0.1, Xcode 27.0). Question: do the M5/M6 GPU Neural Accelerators help Apertura? Answer: yes —
prefill 2-3× on every small model, decode unchanged, fidelity unchanged. Only small models fit
(E2B, E4B, 12B).

## Later the same day — 26B-A4B, mlx-lm comparison, two prefill fixes
- 26B-A4B (15.8 GB) fits the M6's 19.07 GB working set (peak footprint 16.1 GB); decode
  44-47 tok/s (2.7× the dense 12B: ~4B active), but prefill ~130-140 tok/s at every length and
  NAX barely mattered. Cause: `ESExperts::sparseForward` called `gather_qmm` unsorted → MLX ran
  seq×k M=1 matvecs. **Fix:** sort (token, expert) pairs by expert when seq·k ≥ 64 (mlx-lm's
  `_gather_sort`), `sorted_indices=true`, scatter back. Probe (1024 tok × top-8 of 128, 26B
  gate_up shape, vs fp32 CPU `gather_mm`): sorted rel-L2 4.70e-3 vs unsorted 7.86e-3. 26B
  prefill @4096: 616-636 (NAX) vs 391 (no NAX); old ~140. Shorter prompts were swap-polluted.
- BaseRT paper (arXiv 2607.19438, M5 Pro) shows MLX at 12,355 tok/s E2B Q8 prefill @2048.
  mlx-lm 0.32.0 / MLX 0.32.3 on this M6: `mlx_lm.benchmark` reports 8,940 tok/s (QAT 4-bit) —
  but its full forward measures 2,733 (Apertura 2,548). The difference: mlx-lm's prefill evals
  only the caches, and E2B has 15 caches for 35 layers, so the 20 shared-KV layers are never
  computed for prompt tokens (cache-only prefill 9,395 tok/s). Same kernels otherwise: Q4 g32
  vs g64 qmm 14.7 vs 16.2 TFLOP/s, bf16 GEMM 18.3 TFLOP/s on the M6.
- **Fix:** `ESGemma4TextModel::forward(…, lastOnly)` — from `firstKvSharedIdx()` on, slice h,
  RoPE, masks and PLE inputs to the last row; `lastLogits` passes it (full-logits `forward`,
  `forwardTrace` unchanged). E2B 2,477 → 5,932 @2048, 6,237 @4096; E4B 1,440 → 2,252 @2048.
  Fixture conformance 14/14 + greedy MATCH (unfused/fused); 256-tok greedy chat identical to
  the pre-change binary on both test prompts. Prefill chunk size (512 default) was ruled out
  first: 512 / 2048 / unchunked all ~2,550 @2048.
- README table updated (post-fix numbers, 26B row, a "prefill skips" paragraph).
- Not run: the full XCTest suite (most fixtures aren't on this machine), `--vs-bf16` on 26B
  (51.6 GB source won't fit 24 GB — do it on the M4 Max).

## Evening — tracing the remaining gap to mlx-lm
- MLX 0.32.3 (worktree `../mlx-0323`, `gated_delta_update_nax` dropped from the kernel build —
  it still fails on the macOS 27 SDK): +2-11% prefill at short prompts, nothing at 2-4K. Pin kept.
- Causal SDPA mode instead of the explicit additive mask (env-gated experiment): no effect, reverted.
- Metal System Trace (`xctrace`, command-buffer intervals): ~150 ms of GPU idle at the start of
  every cold `--bench-eager` prefill = MLX building pipeline states on first use. New
  `APERTURA_BENCH_WARM=1` (throwaway prefill first): E2B 5,978 → 7,465 tok/s @2048.
- Xcode GPU captures (`APERTURA_GPU_CAPTURE`, `~/Documents/GitHub.nosync/Resources/Traces/`):
  Apertura 344.9 ms GPU / 7,283 dispatches / 196 encoders vs mlx-lm 300.5 ms / 1,444 / 79 for a
  2K E2B prefill. Kolja's timeline screenshots showed four segments — one per 512-token chunk,
  each ending in a burst of tiny dispatches (the shared-KV layers on that chunk's last row).
- Fixes: middle chunks pass `cacheOnly` and stop before the shared-KV layers (exact: greedy
  identical at chunk 512, fixtures 14/14); elastic models default to 1024-token chunks
  (`ESModelConfig::fromConfigJSON`; AperturaKit `prefillChunkLength` default is now -1 = engine
  default, Settings field empty = auto). Warm, median of 3, 512 → 1024: E2B 8,027 → 7,973 @2K,
  7,175 → 7,783 @4K, 6,181 → 7,065 @8K; E4B +5-9%; 12B 1-2% slower with 1024, so it stays at 512.
- App note: models already registered keep their stored chunk length (512) until reset in
  Settings; KV snapshots fingerprint the chunk size, so E2B/E4B snapshots rebuild once.

## Network (machine-local, not a code issue)
- Every network-touching `hf` call hung (download, `auth login`, even with `--token`). Root
  cause: the Linksys router (`d8:ec:5e:82:76:46`, also the IPv4 gateway) advertised an AT&T
  IPv6 prefix (`…:22f::/64`) it didn't route; Python's HTTP stack waits on the AAAA address
  forever (socket in SYN_SENT), while curl/browsers fall back to IPv4 (Happy Eyeballs). Not the
  dual Ethernet + Wi-Fi setup — v6 failed on each interface alone. Kolja put the Linksys into
  IPv6 bridge mode; v6 now comes from the AT&T gateway (`3c:71:4b:09:7f:71`, `…:220::/64`) and
  works on both interfaces; plain `hf` works. `~/.local/bin/hf4` (IPv4-forced wrapper) remains
  as a fallback. HF login done by Kolja.
