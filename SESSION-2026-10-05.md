## 1. The elastic port (what `cad9561` does)

`ESCompiledStep` threw on PLE models. Three changes:

1. `ESGemma4TextModel::forwardStep` computes per-layer inputs on device from the
   int32 token-id array (gather + projection + norm, static shapes, so they trace)
   and threads `ESSharedKV` as `forward()` does. New `computePerLayerInputs(const
   mx::array & ids, ...)` overload; the vector form delegates to it.
2. `ESKVCache` step mode chose the scatter index by `maxKeep > 0`. A *storing*
   sliding layer appends with `maxKeep == 0` (keeps full length for the shared
   layers) and would have been scattered at the global index into a window-sized
   buffer. `setStepLayerTypes(vector<bool>)` installs per-layer types; `update()`
   uses them when present, old rule otherwise.
3. The step keeps `owned_` (layers that are not kv-shared) and adopts, feeds,
   collects, compacts and grows slots only for those. Shared-KV layers own no slot;
   they read the storing layer's full-capacity buffer through `ESSharedKV` inside
   the traced forward. `firstS_`/`firstG_` are now indices into `owned_`.

Gates: `--step-verify` E2B Q4 317/317, E4B Q4 317/317, E2B bf16 312/317 @512 (one
near-tie flip, resynced) / 317/317 @1030 / 217/217 @8. `--step-lockstep` E2B bf16:
mean |Δlogit| 0.129, max 0.922, 1/300 flips — inside the 31B's documented ε.

Cold pairs (fresh process, D=300, gate ≤53 °C): E2B Q4 decode 125 → 142 @512
(+13–19%), 118 → 138 @4096 (+17%); E4B Q4 81 → 89 (+9–10%); E2B bf16 70 → 76.
The gain scales inversely with model size: small models are dispatch-bound.

## 2. Fast-math experiment (negative, documented in roadmap §3)

Rebuilt MLX with `-ffast-math` in `mlx/backend/metal/kernels/CMakeLists.txt` and
`MathMode::Fast` as the `CompileOptions` default in
`mlx/backend/common/metal_kernel.h` (both reverted after the build). Results on E2B:

- Speed: zero. 16 cold arms, all deltas inside noise. First-run prefill reads low
  because the new generated kernels JIT; vanishes on repeat.
- Numerics: 4-token per-op conformance bit-identical to the safe build (17 ops,
  logits included — bf16 output rounding hides fp32-ULP differences; MLX pins
  rsqrt/sqrt/log/tanh to `metal::precise`). 1408-token long-context oracle: max
  |Δlogit| vs PyTorch 1.250 fast vs 1.125 safe, argmax and 32 greedy tokens match
  on both. Free-running greedy on a real 70-token prompt diverges from the safe
  build after ~40 tokens.
- Verdict: an ε mode that buys nothing. Do not adopt.

Tools used: `scripts/compare_dumps.py` (diffs two `--dump-mlx` outputs against the
fixtures), `scripts/gen_longctx_e2b.py` (a scratchpad copy of
`Tools/generate_longctx_fixture.py` with E2B, War and Peace as the document, and
32 greedy tokens; output went to the scratchpad and is gone — regenerate if needed).

Pre-existing finding, unrelated to fast math: the E2B short-prompt greedy gate
("The quick brown fox", 20 tokens) MISMATCHES the PyTorch/MPS oracle on the safe
build too — same 3-token cycle, phase-shifted at tokens 7 and 15. Degenerate
prompt; the long-context oracle with a real document passes. Worth a cleaner
short fixture prompt at some point.

## 3. Bundles

- Published today: **`apocryphx/gemma-4-E4B-it-q4-apml`** (public, 8.77 GB, Q4 g64 +
  Q8 embeddings, `--verify-bundle` max |Δlogit| 0.000, README/license mirror the
  E2B repo). Export + gate + upload chain: `scripts/export_e4b.sh`, `scripts/upload_e4b.py`.
- `apocryphx/gemma-4-E2B-it-q4-apml` already existed with the same recipe (6.28 GB).
- **Size lever found:** `exportQuantizedBundle` (ESWeightLoader.mm) quantizes
  `embed_tokens.weight` at `embedBits` and layer projections at `bits`; everything
  else stays bf16, including `embed_tokens_per_layer` — 2.35 B params, 50.5% of
  E2B, 4.7 GB of the 6.28 GB bundle. Analytic: Q8 PLE → ~3.9 GB, Q4 g64 PLE →
  ~2.8 GB. The table is only read by per-token gather, so the change is: one more
  rule in the exporter, a quantized-aware load of that tensor, and a dequantize
  after `mx::take` in `computePerLayerInputs` (MLX's quantized-embedding pattern).
  **DONE later the same day: `b949f1e`.** See roadmap §1c for the table of results.
  Summary: Q8 table is free (identical `--vs-bf16` agreement to bf16, prompt by
  prompt, on 144 short and 256 long positions; `--verify-bundle` Δ0; `--step-verify`
  317/317); E2B bundle 5.9 → 3.8 GB, Q4 table 2.7 GB. Decode neutral. Two benchmark
  artifacts to know: in-memory `--quant-ple` pays the lazy quantize inside the first
  prefill; from a bundle the first prefill is faster because fewer bytes page in.
  HF repos updated to Q8-table bundles (E2B 4.08 GB; E4B 6.13 GB, 5.7 GB on disk,
  `--vs-bf16` long prompt 240/256 = 93.8% vs E2B's 78.9% on the same prompt). Scripts:
  `sessions/2026-10-05/scripts/ple_tests*.{sh,py}` in Auteur-Studio.

## 5. Methodology reminders

- Gate thermals at idle floor + 1–2 °C, not an absolute 48 °C (37 °C ambient today;
  die idles 50–53). `Tools/hidtemp.m` builds with
  `clang -fobjc-arc -O2 Tools/hidtemp.m -framework Foundation -framework IOKit -o hidtemp`.
- Use Python `time.sleep` for gate loops in background jobs; zsh `sleep` stalled.
- One GPU job at a time. Chains were serialized by polling a "=== done ===" line.
- `--bench`'s two in-process arms ignore the quant flags' effect in a misleading
  way (identical bf16/Q4 rows); use `--bench-eager` / `--bench-step`.
